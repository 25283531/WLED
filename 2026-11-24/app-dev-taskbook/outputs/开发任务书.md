## 0. 总览

### 0.1 当前事实基线（实测 + 代码）

1. **固件源码比设备固件新**
   - 源码里已有 222 个效果（0–221），其中 221 = `FX_MODE_LUMI_AURORA`「极光之舞」：
     `firmware/wled00/FX.h:377`、`firmware/wled00/FX.cpp:5208-5321`、`FX.cpp:11431` 的 `addEffect(...)`。
   - 实测设备 `/json/info` → `fxcount: 220`，`POST /json/state {"seg":[{"fx":221}]}` 返回 success 但回读仍是原值 → 设备上没有 221。
2. **硬件事实（已确认，覆盖此前的 15×23/345 描述）**
   - 灯珠：**布局 9 列 × 23 颗（逻辑 207）**，**单线数据 GPIO10**；**S 形（蛇形）走线**：第 1 列底部第一颗为 **1 号位**，向上到第 1 列顶部（23 号），
     第 24 颗从第 2 列顶部向下，第 46 颗落在第 2 列底部。
   - **第 46 颗已物理拆除、数据线短接**（v1.6 更正，此前「损坏但仍在链上」作废）：灯带实际只有 **206 颗**，
     固件仍按 207 颗下发，因此第 46 颗之后**整链前移一格**（第 47 颗显示第 46 颗的数据，依此类推，最后一个数据包没有灯承接）。
     这是此前「颜色跳号、红色出现两次、点亮位置落错列」的主因，残留段叠加只是次要因素。
   - **修正口径**：逻辑矩阵保持 **9×23 = 207**，用 `/ledmap.json` 把 206 颗物理灯按真实位置一一映射，
     被拆位置（逻辑 (x=1,y=22)，行主序下标 199 = 物理第 46 颗原位）不分配物理灯；APP 遮罩同一格留空。
     **不要**把 `count` 改成 206 让矩阵少一格（细节见 §0.1 第 14 条）。
   - **第 1 列在最左**（相对 9×23 展开后的逻辑矩阵）；`DEFAULT_MATRIX_RIGHT_START=0` 即为该方向，现有配置已正确。
   - 实物为 φ50 mm 圆柱，9 列灯珠贴在圆柱外表面；**正视只看到中间 7 列**（视觉上第 1、9 列在背面接缝），
     设备页发光区因此只取 **7 列 × 23 行**；正视可见即第 2–8 列（已确认）。
   - 平台：**立创实战派 ESP32-S3 开发板**（WROOM-1-N16R8：16 MB Flash / 8 MB PSRAM），产品原型开发用；
     `esp32lichuang` 临时子目录/固件环境**保留且为必需**（见 T9）。
   - 设备当前配置错误：`/json/info` 报 `count=345 / matrix 15×23`，`cfg.hw.led.ins[0]={len:206,pin:[10]}`、`cfg.hw.led.matrix=9×23`；刷机后必须统一校正为 **207 / 9×23 / pin 10**。
   - **布局不生效的根因（M0 实测）**：设备上残留旧 `/ledmap.json`（`width=15,height=23`，346 项）会覆盖 `cfg.hw.led.matrix` 面板配置，使 `Segment::maxWidth/maxHeight` 仍为 15×23、`getLengthTotal()` 返回 346。
     写入 207/9×23 面板**必须同时删除 `/ledmap.json` 再重启**（`GET /edit?func=delete&path=/ledmap.json`），否则仅改 cfg 不会生效。
   - 矩阵宏：`DEFAULT_MATRIX_VERTICAL=1`、`DEFAULT_MATRIX_SERPENTINE=1`、`DEFAULT_MATRIX_BOTTOM_START=1`、`DEFAULT_MATRIX_RIGHT_START=0`（第一列最左）。
3. **音频律动：设备端已带 usermod；麦克风按原理图为「模拟麦 + ES7210 ADC」**
   - `/json/info` → `um: [32]`（32 = `USERMOD_ID_AUDIOREACTIVE`）。
   - `/json/cfg` → `um.AudioReactive.enabled = false`，`digitalmic = {type:1, pin:[32,15,14,-1]}`，`sync = {port:11988, mode:0}`。
   - 临时开启 `{"AudioReactive":{"enabled":true}}` 后 `/json/info.u.AudioReactive` 返回
     `Audio Source: "not initialized - check pin settings"`、`Sound Processing: "suspended"`；
     已还原为关闭，设备状态与开始时一致。（**v1.6 已解决，见下**）
   - **M0 刷机后复测结论相同**：仅写入 I²S 引脚与 `SR_DMTYPE=1` 不足以驱动 ES7210，必须在 T2.3.1 补 I²C 初始化；M0 不宣称音频链路可用。
   - **v1.6 结果（2026-11-24）**：ES7210 I²C 初始化已内置到 usermod（`AR_ES7210=1`、`dmType=4`、MCLK/LRCK=512），
     CI 产物已 OTA 到 `10.0.1.172`；`cfg.um.AudioReactive = {enabled:true, digitalmic:{type:4, pin:[12,13,14,38]}}`，
     重启后 `/json/info.u` 实测：`Audio Source = ["I2S digital"," - quiet"]`、`Sound Processing = ["running"]`、
     `Manual Gain = [1.56,"x"]`，**不再出现 `not initialized - check pin settings` / `suspended`**；
     `info.leds.count=207 / matrix 9×23` 与 `/ledmap.json` 均保持不变。**音频源初始化与处理任务均通过**。
   - **v1.6 真拾音与律动实测（2026-11-24，通过）**：用户实地播放音乐，连续 10 次（间隔 1.5 s）读 `/json/info.u`，
     `Audio Source` 为 `peak 75 / 75 / 53 / 85 / 58 / 97 / quiet / 95 / 95 / 75 %`，`Sound Processing` 恒 `running`；
     第二组 55 次采样 `peak%` 均值 79.9（55/55 有声）。效果侧功率对照（`bri=153`，彩色 ≤60%）：
     `Solid(0)` 恒 2604 mA，`GEQ(139) sx=64/ix=240` 为 452–1999 mA（Δ1547），`PS GEQ 2D(198)` 为 346–1083 mA（Δ737），
     非音频的 `Noise2D(146)` 为 2712–2768 mA（Δ56，反例）。用户目视确认「音律灯效测试正常」。
     → **T2.3.1 音频硬件链路（ES7210 → I²S → usermod → FX）验收通过**；细节见 `work/evidence-device.md`。
   - **原理图核实**（`https://wiki.lckfb.com/zh-hans/szpi-esp32s3/open-source-hardware/` 对应原理图 `ESP32-S3-V1_0_1`）：
     - 麦克风是**双路 ZTS6216 模拟麦克风**（MIC1/MIC2，模拟输出），不是单颗数字 MEMS 硅麦；
       数字接口在 **ES7210** 四通道音频 ADC 上（I²C 地址 `0x41`，SCL=IO2、SDA=IO1；开发板用了 3 个通道，
       第 3 通道由 ES8311 的 `OUTP/OUTN` 回环）。
     - ES7210 → ESP32-S3 的 I²S：**BCK=IO14、WS=IO13、MCLK=IO38、SDOUT1→DI=IO12**；
       ES8311（DAC，I²C `0x18`）的 I²S：BCK=IO14、WS=IO13、MCLK=IO38、DO=IO45。
     - **定稿**：麦克风为双路 **ZTS6216 模拟麦 + ES7210 四通道 ADC**；固件不能只配 `SR_DMTYPE=1` 就读到数据，
       必须先按 ES7210 寄存器表做 I²C 初始化（时钟/麦克风偏置/PGA），见 T2.3.1。
     - **IO1 冲突处理**：IO1 是 ES7210 的 I²C SDA，**不再作为按键输入**；`BTNPIN` 只保留 IO0/IO3/IO7。
       若实物必须用 IO1 做按键，只能改板/改用其它 I²C 引脚，固件不把 IO1 复用为按键。
   - `platformio_override.ini:51-56` 的 `SR_DMTYPE=0 / AUDIOPIN=4`（模拟）是 C3 旧板配置，与立创 S3 无关，需替换。
   - 现有 `digitalmic.type=1` 只是历史配置（IO32/15/14 在 S3 上也不成立），需按上表重写。
4. **APP 侧没有任何音频能力**
   - `AndroidManifest.xml` 无 `RECORD_AUDIO`，也无 `MediaProjection` / 内录音频相关代码；
     全仓无 `AudioRecord` / FFT / 音频 UDP 发送实现。
   - 「律动」只是把 `EffectMood.MUSIC` 的效果当普通静态效果下发。
   - 新口径要求：切走/退到后台仍要持续采集，只有一键停止或 APP 进程结束才停止。
   - **音频形态已定：A + C 双路**。
     A. 优先内录其他 App 的媒体声音（`MediaProjection` + `AudioPlaybackCapture`，每次会话需授权）；
     C. A 不可用时降级为手机麦克风（`RECORD_AUDIO`）。
     **降级判定只能用静音检测**：Android 不会告知是哪个 App 拒绝内录，声明禁止采集的 App 只会返回一路静音；
     已授权后若连续若干秒 RMS 接近零，先弹框询问「手机现在是否正在播放音乐」，用户确认后才切 C（见 T2.3）。

## T2. 音频链路：A 内录 + C 麦克风降级（静音检测）+ 设备 ES7210 麦克风

### 2.1 现状

- APP 无 `RECORD_AUDIO`、无 `MediaProjection`、无 `AudioRecord` / `AudioPlaybackCapture` / FFT / UDP 发送。
- 固件 usermod 支持 `SR_DMTYPE_NETWORK_ONLY = 254`（`audio_reactive.cpp:766,1464,1494`）：
  仅接收网络音频、不初始化本地麦克风，正好对应「手机当音频源」。
- 实测设备：`um.AudioReactive.sync = {port:11988, mode:0}`、`enabled=false`；网络接收通路存在但未启用。
- 设备页目前没有音频来源选项（`ui/settings/SettingsScreen.kt` 只有亮度/同步/开机状态等）。
- 设备麦克风按原理图为**双路 ZTS6216 模拟麦 + ES7210 四通道 ADC**，不是单颗数字 MEMS 硅麦：
  - I²C：`0x41`，SCL=IO2、SDA=IO1；ES7210 使用 3 个通道，第 3 通道由 ES8311 `OUTP/OUTN` 回环；
  - I²S 到 ESP32-S3：BCK=IO14、WS=IO13、MCLK=IO38、SDOUT1→DI=IO12；
  - 上游 WLED usermod **原本没有 ES7210 支持**（`dmType` 仅 0/1/2/3/5/9），只配 `SR_DMTYPE=1` 不会初始化 ES7210；
    本项目已在 usermod 内置 `AR_ES7210`（`dmType=4`）驱动，见 2.3.1。
- 历史配置 `digitalmic={type:1,pin:[32,15,14,-1]}` 初始化失败；v1.6 已改为 `{type:4,pin:[12,13,14,38]}` 并验证初始化通过。
- **音频形态已定：A + C 双路**（A 内录其他 App 媒体，失败/静音时按用户确认降级到 C 手机麦克风）。

### 2.2 目标行为

1. 设备页新增「音频来源」：**设备麦克风 / APP**，选择持久化，重启后保持。
2. 选「APP」后默认走 **A 内录**；A 不可用时按 2.3.6 的流程降级到 **C 手机麦克风**。
3. **不允许静默切换**：静音检测命中后先弹框询问「手机现在是否正在播放音乐」——
   - 选「是」→ 再提示「即将改用手机麦克风采集声音」，用户确认后切到 C；
   - 选「否」→ 提示「请先打开媒体播放软件并开始播放」，本次**不降级**，继续停留在 A。
4. 降级判定只依据**静音检测**，不得实现「查询某 App 是否允许内录」：
   Android 不提供该信息，声明禁止采集的 App 只会返回一路静音。
5. 计算 16 段 GEQ / 音量 / 峰值，经 UDP 发到设备 `11988`。
6. **切走/退后台/锁屏必须继续采集与发送**，不允许因为 Activity 不可见或屏幕关闭而中断。
7. **只有两种结束方式**：
   - 用户在通知或设备页点「一键停止」；
   - APP 进程被系统或用户结束（含强制停止）。
   划掉最近任务、锁屏、切换前后台都**不应**停止。
8. 常驻通知可见、可停止，文案区分「内录媒体」/「麦克风收音」。
9. 设备端音频源状态（`device` / `network` / `not initialized`）在 APP 可见；断连、无授权、投屏 token 失效都有明确提示。
10. 选「设备麦克风」时走 2.3.1 的 ES7210 配置（`dmType=4`）；驱动已落地（v1.6），该项可直接启用，无需再置灰。

### 2.3 技术方案

1. **设备端麦克风（ES7210，按原理图，非独立任务）—— 已实现并初步验证（v1.6）**
   - 依据 `https://wiki.lckfb.com/zh-hans/szpi-esp32s3/open-source-hardware/` 对应原理图 `ESP32-S3-V1_0_1` 确认：
     MIC1/MIC2 为 **ZTS6216 模拟麦**，经 ES7210（I²C `0x41`）转 I²S；ES8311（I²C `0x18`）是 DAC。
   - 引脚与宏写入 `firmware/platformio_override.ini` 的 `[env:esp32lichuang]`：
     `I2S_SDPIN=12`、`I2S_CKPIN=14`、`I2S_WSPIN=13`、`MCLK_PIN=38`、`SR_DMTYPE=4`、`AR_ES7210=1`、
     `ES7210_ADDR=0x41`、`ES7210_SDA=1`、`ES7210_SCL=2`。
   - **已实现**：`audio_source.h` 新增 `ES7210Source`，在 I²S 初始化前完成 **ES7210 寄存器初始化**
     （复位、MCLK 分频、24 bit、MIC1/MIC2 PGA 24 dB、MICBIAS、TDM 通道映射），`audio_reactive.cpp` 的 `case 4` 走该源；
     采样率 22.05 kHz、MCLK/LRCK = 512。旧设备需把 `cfg.um.AudioReactive.digitalmic.type` 改为 **4**（并写 `pin=[12,13,14,38]`）。
   - **按键冲突**：现有 `BTNPIN=0,1,3,7` 中 IO1 与 I²C SDA 冲突，必须从按键列表移除；IO3/IO7 是 DVP 脚，需按实物核对。
   - 启动自检：I²C 扫描不到 `0x41`、I²S 读数为全零、引脚与灯带 IO10/按键冲突时，在 `/json/info.u` 明确报错并关闭音频，
     不允许静默 `enabled=true`（固件 `:1481` 会关闭 usermod）。
   - 参数：`gain/squelch/AGC` 已有（实测 `gain=60, squelch=10`），补充 `dynamics.rise/fall`；
     `/json/info.u.AudioReactive` 输出源类型、`peak`、`FFT_MajorPeak`。
   - 噪声门：低于 `squelch` 时 volume/FFT 置 0；首次上电做 2 秒底噪采样并回写建议值。
   - ES7210 第 3 通道是 ES8311 播放回环，只用于板载自测，不作为「内录其他 App」的来源。
2. **固件侧来源映射**
   - `设备麦克风` → `dmType = 4`（ES7210 + 内置 I²C 初始化）；`APP` → `dmType = 254`（network only）；
   - `cfg.um.AudioReactive.source = "device" | "app"`，启动时映射到 `dmType` 并写回；
   - `UM_AUDIOREACTIVE_ENABLE` 必须编入且 `enabled=true`；网络模式下不初始化本地麦；
   - 收到 UDP 包后复用现有 `AudioSource` 数据通路（FFT/volume）。
3. **APP 侧：后台保活骨架（A/C 共用）**
   - 前台服务 `AudioStreamService`：`startForeground()` + 常驻通知。
   - **`android:stopWithTask="false"`**，`onTaskRemoved()` 不停止采集（仅记录日志）。
   - 通知提供 `ACTION_STOP`，是唯一主动停止入口；`onDestroy` 只在进程结束/系统回收时清理。
   - 权限：`FOREGROUND_SERVICE`、`POST_NOTIFICATIONS`、`RECORD_AUDIO`、`FOREGROUND_SERVICE_MICROPHONE`、
     `FOREGROUND_SERVICE_MEDIA_PROJECTION`；**开始发送时一次性申请麦克风权限**，保证 A→C 降级不需要临时弹权限框。
   - 引导设为「不受限制」（`ACTION_REQUEST_IGNORE_BATTERY_OPTIMIZATIONS`），国产 ROM 另需允许自启动/后台。
   - Android 12+ 禁止后台启动前台服务：必须由用户可见操作（点击「开始发送」）触发。
   - 服务需同时声明 `mediaProjection|microphone` 两种前台类型，按当前源切换；切换时更新通知文案。
4. **形态 A：内录其他 App 媒体**
   - `MediaProjectionManager.createScreenCaptureIntent()` → 前台服务；
   - `AudioPlaybackCaptureConfiguration.Builder(mediaProjection).addMatchingUsage(USAGE_MEDIA).addMatchingUsage(USAGE_GAME).build()`
     构造 `AudioRecord`（Android 10+）；
   - `FOREGROUND_SERVICE_MEDIA_PROJECTION`、`foregroundServiceType="mediaProjection"`；Android 14 每次会话重新授权；
   - **不要写「查询某 App 是否允许采集」**：系统没有该 API；`allowAudioPlaybackCapture=false` 的目标 App 只表现为静音。
5. **形态 C：手机麦克风收音**
   - `RECORD_AUDIO` + `FOREGROUND_SERVICE_MICROPHONE`，`foregroundServiceType="microphone"`；
   - `AudioRecord` 16 kHz / 单声道 / 16 bit，1024 点窗；优先 `MediaRecorder.AudioSource.MIC`，
     可选 `VOICE_RECOGNITION` 降低处理；不对媒体音频强抢占焦点。
6. **A → C 静音检测与降级流程（关键交互）**
   - 状态机：`A_ACTIVE → A_SILENT_SUSPECT → ASK_USER → C_ACTIVE`（用户选「否」则回 `A_ACTIVE`，本次会话不再自动询问）。
   - 触发条件：A 已授权且运行 ≥ 10 s；连续 **5 s** 的 RMS 低于阈值（如 -60 dBFS，按实测校准）；
     避免把「用户主动暂停」「音量极低」「蓝牙输出」误判为禁止内录。
   - 命中后**不静默切换**，弹框询问：「**手机现在是否正在播放音乐？**」
     - 「是」→ 二次确认「即将改用手机麦克风采集声音（该媒体应用可能不允许内录）」；
       确认后停止 A 的 `AudioRecord`、释放 `MediaProjection`、启动 C，通知文案改为「麦克风收音」，

     - 「否」→ 提示「请先打开媒体播放软件并开始播放；本次不降级」，保持 A，不切换。

     不允许后台直接切换。
   - 降级只在当前会话生效；下次启动仍优先尝试 A。设备页提供「重试内录」手动入口。
7. **分析**
   - Hann 窗 + radix-2 FFT；输出 16 段 GEQ（对数分箱 40 Hz–16 kHz）、`volume`、`peak`、`FFT_MajorPeak`。
8. **协议与传输**

### 6.3 技术方案（离线复刻，已拍板）

1. **目录结构**
   ```

     stubs/Arduino.h          # millis/random8/16/map/sin8/cos8/PROGMEM/F()

     render_main.cpp          # 命令行：--fx <id> --frames N --fps 25 --out out.gif
   ```

2. **编译方式**
   - 用宿主 g++ 编译 `FX.cpp` 的效果函数 + 桩层，定义 `-DFX_RENDER_HOST` 跳过硬件相关初始化；

     保证波形可复现；
   - 随机源用固定种子（`srand(42)`）；`millis()` 用虚拟时钟，每帧 +40 ms。
3. **渲染规范（通用预览，已改口径）**
   - 画布：**宽 32 × 高 18**，左侧第一列起算；按通用预览图渲染，**不按实际 9×23 灯珠排列**；

   - 参数固定：`sx=128, ix=128, c1=128, c2=128, c3=16`，`pal=0`，主色白；
   - 帧数：常规 24 帧（≈1 s），慢速效果 48 帧（≈2 s）；25 FPS；
   - 输出：最近邻放大 8 倍 → 256 色 GIF（Pillow），循环播放。
4. **资源与清单**
   - 输出到 `app/app/src/main/assets/effect_previews/<id>.gif`；
   - 生成 `app/app/src/main/assets/effect_previews/manifest.json`：`fxId、name、frames、fps、sha256`；
   - 渲染失败（全黑/异常）记入 `work/gif-failures.md`，CI 不静默通过（覆盖率 < 95% 时失败）。
5. **GitHub 工作流（新增 `.github/workflows/effect-previews.yml`）**

     与现有「CI 只验证、提交由人决定」的约定一致；
   - 与固件构建共用同一 commit：固件 workflow 的 artifact 与预览 artifact 都带 `github.sha`，发布时配对。

   - 设备型号差异（若未来多型号矩阵不同）通过 `model` 选择资源目录，当前只有 `C01`。

   - 动图：`ImageDecoder` 逐帧解码（上限 20 帧、每帧 ≤ 100 ms 归一），按相同管线缩放后重编码 GIF。
4. **编码**：扩展现有 GIF 编码器支持多帧/延时/循环；控制单文件 ≤ 2 MB。
5. **上传**：

   - `POST /upload`，`multipart/form-data`，字段 `data`，文件名 `isle.gif`；

6. **失败处理**：上传失败重试 2 次；仍失败则回滚到上一个效果并提示。
7. **空位（APP 端）**：第 46 颗已物理拆除、数据线短接（§0.1 第 2 条），该格在 APP 映射时**留空/置黑**，不做相邻像素补偿。

### 排序依据

| 顺序 | 理由 |
|---|---|
| M0 先做 | 后续所有验证都依赖「CI 原型固件与源码一致」；也是 9×23/207 与预览的前提 |
| M1 第二 | 效果表是预览、收藏、预设的共同底座；越早清空重设，后续返工越少 |
| M2 第三 | 用户明确要求先做音频；不依赖改板，且能立刻验证网络音频链路 |
| M3 第四 | 预览依赖 M1 的最终 id；按 32×18 通用画布渲染，不再依赖走线方向 |
| M4/M5 靠后 | 工作量最大、涉及面最广；web 中文与外观可并行，但需固件与 APP 同步发布 |
| M6 最后 | 依赖字体授权与子集体积，且与字幕参数、web 中文文案有联动 |
